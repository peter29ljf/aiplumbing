It writes to data/console.db on purpose: a conversation that persisted nothing would not be exercising the half of production most likely to be wrong. What differs is only the switches, shown in the bar above. Each reply says which node answered and what it cost, which is how you tell a slow model from a long walk through the graph.

The last time python3 -m flow.runner.harness ran, read straight off the newest report in flow/runs/. Passing sometimes is not passing — a scenario that goes four for four is a different thing from one that goes three, and only the second is worth a morning.

Everything simulated

This process only, and nothing is written to disk. What production reaches lives in the systemd unit on the server — a switch here that wrote a tracked file would put it back in git, which is the arrangement that once let a git pull silently stop Telegram notifications with nothing reporting an error. Restart the console and everything is simulated again.
A green light means everything a service needs is present, not that it is known good — nothing is sent to find out. To really prove a leg, run python3 scripts/check_live.py --all, which sends.
One tool, written once, run against either world. live — the switch is on and everything it needs is here. blocked — switched on and cannot reach the service. The agent will call it, be refused, and stop dead in the middle of somebody's booking, which from outside looks like the model failing. simulated — it could reach a service and the switch says no. local — never leaves the process.

A tool answers to a service, not to its own name: technician.notify and escalate.raise both reach a person through Telegram, so both stop the moment Telegram does. Remembers is what the engine copies onto the ticket by itself, without the model being asked to write it down as well.

Which nodes hold a tool is read-only here. It lives in flow/flow.yaml beside a paragraph naming the failing run that put it there, and writing that file back from a form would delete every one of those comments. What a node may do and why it may do it are the same fact.
Saving writes straight to the file under flow/ and records a timestamped snapshot in prompt_history/, so it can be rolled back. It takes effect on the very next message — there is no restart between editing a rule and a customer reading it, so run the scenario suite before trusting a change: python3 -m flow.runner.harness --repeat 3. The suite is noisy; compare across repeats rather than believing one run.

Where a rule sits inside its file matters. A paragraph added above a routing table pushed the distinction below it down far enough to start being missed, and one scenario went from four out of four to one out of three on nothing but the ordering.
Every edit the self-healing loop has made to a prompt. Live changes are in the files right now; reverted ones were tried and rolled back because they did not fix the scenario or broke another one. The prompts you reviewed are the baseline — this is everything that happened to them since.
