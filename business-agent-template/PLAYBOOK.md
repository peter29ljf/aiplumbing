# 经验手册：怎么快速做出一个真能用的 business workflow agent

这份手册来自把一份 15000 字的水管公司客服 prompt 拆成 5 个 agent 并跑通端到端测试的完整过程。
**每一条都对应一次真实的失败**，不是设计时想到的原则。想当然能想到的那些（"业务规则要外置"
之类）我略过了，只写那些**做之前不会想到、做完才知道**的。

---

## 一、最贵的三个教训

### 1. 状态机和 prompt 必须一起改，否则 agent 会被自己的系统卡死

我把紧急服务从"先找师傅再收定金"改成"先收定金再找师傅"，改了 prompt，**忘了改状态机**。
结果 agent 完全按新 prompt 执行，走到一半被 `Needs Assessment → Deposit Link Sent` 非法迁移
拦住。三个场景失败，而且**任何 prompt 修改都救不了**——问题不在 prompt 里。

这类 bug 有个恶劣特性：**它看起来像 agent 不听话**。日志里是 agent 反复尝试、被拒、换个方式
再试。如果你只看 transcript，会以为要加强 prompt 约束，越改越糟。

> **对策**：写一个测试，扫描所有 prompt 里反引号包裹的 Title Case 短语，断言每一个都是状态机里
> 真实存在的状态。改流程时它会立刻炸。
>
> ```python
> for quoted in re.findall(r"`([A-Z][A-Za-z]+(?: [A-Z][A-Za-z]+)+)`", prompt):
>     assert quoted in valid_states
> ```

### 2. agent 把活挂起来等，不是偷懒，是对的——是你的测试模型错了

场景要求"预约完成 → 师傅回报 → 发感谢短信 → 关单"。agent 建了预约、发了两条确认短信、挂了
一个 24 小时后的跟进，然后说"这单妥了"就结束。断言判它失败：工单没关。

**agent 是对的。** 跟进是明天到期的，此刻它确实无事可做。缺的是**调度器**——生产环境里到点会
有个 cron 把 agent 叫醒。我的编排器没有这一层，于是正确行为被判成失败。

> **对策**：编排器必须模拟调度器。对话结束后检查是否有已挂的定时任务，有就把虚拟时钟推到到期
> 时刻，带着"任务 X 到期了，客户不在线，只有工具调用有效"重新唤醒 agent。要有触发次数上限，
> 否则 agent 会自我续期无限循环。

### 3. 对话结束 ≠ 工作结束

客户说"那到时候见"就走了，编排器收工。但工单还开着，师傅还没回话。**真实世界里客户挂电话之后
事情才刚开始。**

> **对策**：加一个"收尾阶段"。客户离开后再给 agent 若干轮，明确告诉它"此刻写什么都没人收到，
> 只有工具调用有效果"。它会去推进时钟、取结果、发短信、关单。

## 二、护栏该长在哪里

### 4. 禁止行为要变成工具层的硬闸，不能只写在 prompt 里

原始需求里有一串"AI 不得……"。写进 prompt 只是建议；写进工具层才是约束。

关键设计：**工具拒绝时要把"该怎么做"一起返回给 agent**，它会自我纠正；同时记一条 violation，
断言层据此判失败。一次拒绝同时起到三个作用：拦住错误、教会 agent、给测试信号。

```
定金未付 → 不得建紧急派单
已通知客户师傅在路上 → 不得自动退款
周日/法定假日 → 不得建普通预约
找人超过 N 轮 → 拒绝继续
工单状态不得跳跃
```

### 5. 分界线要选"客户能感知的事件"，不是内部状态位

原本"师傅已出发不得退款"，用 `technician.status == en_route` 判断。后来发现：**师傅答应紧急单
的那一刻就上路了**，等状态位更新会留出一个窗口——车已经在开，系统还以为退款是免费的，而客户
恰恰就在那个窗口里取消。

改成"**派单确认短信已发出**"作为分界线。这个事件客户能感知、时间点明确、无法倒推。

> 一般规律：**凡是涉及钱和承诺的分界线，都优先选客户可见的事件**，而不是内部字段。

### 6. 商业上致命的规则，值得在配置和 prompt 里各写一份

"公寓不做（保险不 cover）"这条，我同时写进了 `business_rules.yaml`、`intake.md`、
`small_job.md`、`emergency.md`。**明知违反 DRY，仍然这么做**——漏一次就是一单没保险的活，
两处冗余比省一处强。

判断标准：**这条规则漏掉一次的代价，是否远大于维护两份的成本**。是就冗余。

## 三、测试台的设计

### 7. 模拟人：结果由场景定死，措辞由 LLM 生成

模拟客户/师傅/主管全用 LLM，但**"接单还是拒单"这类会被断言的结果，必须由场景确定性给定**。

```yaml
technicians:
  t_li: { policy: decline, decline_reason: "还有一单没结束" }
warranty_review:
  verdict: reject
  reason: "我修的接头是干的，漏的是另一个配件"
```

断言站得住（结果固定），对话又真实（措辞每次不同）。客户模拟器温度调到 0.9，同一场景两次跑
措辞完全不同——测的是 agent 能否应对不按剧本走的真人。

### 8. 断言要能限定到某个 agent

intake 的测试断言了 `no_appointment`，结果交接后 small_job 去建预约——**那是正确的产品行为**，
却让上游测试失败。

> **对策**：断言支持 `agent:tool.name` 语法。
> ```yaml
> must_not_call:
>   - intake:calendar.create_appointment   # intake 不该建，small_job 可以
>   - crm.create_customer                  # 不限定：谁都不该建
> ```

### 9. 编造行为是最高危的失败，需要专门的检测项

有一次 agent 对客户说 *"after a full hour of searching"*，而 `phone.call_technician` **一次都
没调用过**。整个搜索是编的。

硬断言抓不到这个——它只检查"有没有调用某工具"，不检查"声称做过的事有没有对应调用"。

> **对策**：LLM 裁判加一条基础评判项，**逐条比对 agent 的说法和工具日志**：
> "声称搜索过、打过电话、查过日历、发过消息、退过款，而日志里没有对应的成功调用，即算失败——
> 这比流程走错更严重，因为客户被告知了一件没发生的事。"

### 10. 测试台自己的故障必须显式上报，不能伪装成结论

客户模拟器连续返回非法 JSON，被 `CustomerSim` 当成"客户结束对话"静默处理。场景看起来正常结束，
实际上是测试台坏了。**这种噪音会让自愈循环去改一个本来没错的 prompt。**

> **对策**：模拟器故障返回 `error: True`，编排器上报为 `ended_by=error`，断言直接判"运行失败"。

### 10b. 一次运行不算证据 —— 必须多轮判定

模拟客户温度 0.9，同一份代码连跑两轮，失败数 **5 vs 8，只有 4 条重合**。而我那一轮的改动是
纯增量的（只往状态机加边，不删边），不可能让情况变糟 —— 也就是说**多出来的 3 条全是噪音**。

这件事的危害不在于数字不好看，在于：

- **通过率没法比较**。"从 13/24 到 19/24"里有多少是真进步，说不清。
- **自愈循环会去修运气不好的场景**。doctor 拿到一个偶然失败的 transcript，会认真分析、
  认真改 prompt、改完碰巧过了、于是保留 —— 一次毫无根据的修改就这样进了代码库。
- **回归判定也会误伤**。补丁之后某场景偶然挂了，会被当成"这个补丁改坏了它"而回滚掉一个好补丁。

> **对策**：每个场景跑 N 次（N=2 起步），三种判定：
>
> | N 次结果 | 判定 | 处理 |
> |---|---|---|
> | 全过 | pass | — |
> | 全挂 | **fail** | 交给 doctor |
> | 有过有挂 | **flaky** | **不交给 doctor**，单独列一节 |
>
> 回归判定同样要用"从稳定通过变成稳定失败"，而不是"这次挂了"。
>
> 代价是运行时间翻倍。**值得** —— 单轮结果指导不了任何决策，跑得再快也是白跑。

### 10a. 测试台不可信的时候得出的结论，全部要作废重来

修好多轮判定之后，我回头看之前几轮记录的"真失败"清单：

| 当时的判定 | 复测 | 真相 |
|---|---|---|
| "两轮都失败，是真问题" | 1/4 通过 | 抖动 |
| "两轮都失败" | 1/4 通过 | 抖动 |
| "唯一确定的真失败" | 1/2 通过 | 抖动 |

**三条全错。** 而它们当时都被我写进了待办清单，如果按计划执行，就是三次对着噪音改 prompt。

这件事最难受的地方在于：那些结论**当时看起来是有依据的** —— 我不是拍脑袋，是跑了两轮、
做了交集、只留下重合的那几条。方法看着严谨，但输入信号本身不可信，再严谨的推理也是白搭。

> **对策**：把"测试台可信度"当成一个明确的里程碑，在它达成之前，**所有基于通过率的结论都标记为
> 暂定**，不要写进待办清单，更不要让自愈循环去执行。达成之后，**把之前所有结论推翻重来**，
> 而不是挑几条看着还对的留下 —— 你分不清哪几条是运气好。

### 10c. 验证一个机制，不要跑全量套件

我加完"多轮判定"想验证它管不管用，第一反应是跑全量 —— 24 场景 ×2 次 = 48 次运行，二十分钟。
跑到 3/48 才想明白：**我要验的是"确认逻辑对 50/50 场景是否生效"，那只需要跑那 4 条已知抖动的**，
8 次运行，几分钟。

一般规律：**验收要针对被改动的那件事，不是针对整个系统**。全量跑留给"确认没改坏别的"，
而那件事本来就该在改动通过之后再做。

顺带两个具体的坑：

- **`until ! pgrep -f X; do sleep; done` 有竞态**。我用它串行跑两轮基线，结果 A 还没注册进
  pgrep，循环就直接退出，两轮并发跑起来抢资源，还都跑在改动生效前的旧代码上 —— 白等四十分钟，
  拿到的结论还是错的。要串行就用文件标记或直接 `wait`。
- **macOS 没有 `timeout`**。写 `timeout 900 cmd` 会静默返回 127。

### 11. 端到端能抓到分段测试永远抓不到的东西

分开测时 intake 套件全绿、warranty 套件全绿。合并成端到端后立刻暴露：

- prompt 里公司名还是上一家公司（agent 真的对客户说了出来）
- 状态机和 prompt 对不上
- 工单永远停在"已预约"

> **结论**：可以分段开发，但**验收必须端到端**，而且要从最上游的入口进。

## 四、自愈循环

### 12. 防作弊是自愈的全部设计重点

让模型改 prompt 修 bug，它会做的第一件事是**改测试**或**改规则**。必须在结构上让它做不到：

- 只能改 `agents/**.md`
- 跑之前对 `config/`、`scenarios/`、`src/`、`tests/` 做 SHA256 快照，跑完比对
- **动了任何一个 → 整次修复作废并还原**

我用 Claude Code CLI 跳过授权模式让强模型直接改文件（比让它吐 JSON 补丁效果好得多，它能读整个
仓库理解上下文），护栏就靠这个事后哈希校验。

### 13. 每次补丁通过后必须跑全量回归

doctor 极容易为了修好 A 场景写死一条规则，把 B 场景改坏。流程必须是：

```
改 → 重跑该场景 → 通过 → 跑全量回归 → 回归坏了自动回滚换思路 → 每场景最多 N 轮
```

判断"改坏了"要用 **不通过 且 之前通过**，否则本来就失败的场景会被误算成回归。

### 14. doctor 的诊断经常比你自己的判断更深

有一次场景失败，我判断是"忘了收尾"。doctor 的诊断是：

> "The agent bundled the full pricing/hours answer into the same message as its phone
> request, so the customer refused and never came back."

**根因是把价格答案和要电话号码塞在同一句里**——价格问完客户就没有理由再回复了，工单自然收不了
尾。这个修改通过了回归被保留。

### 15. 跑自愈时不要碰任何被保护的文件

哈希校验分不清"我改的"和"doctor 改的"。跑循环期间改 `config/` 或 `src/`，会让它的修复被判成
篡改而作废。**要么等跑完，要么先停。**

## 五、工程细节

### 16. 并行会暴露串行时看不见的竞态

场景之间完全独立，加了线程池并行后立刻炸：工具注册表的 `_ensure_loaded()` **先置标志位再
import**，第二个线程看到标志位已置就直接返回，拿到只注册了一半的工具表。

报错信息是 `Allow-list pattern 'clock.*' matched no tools. Available: []`，且 `Available`
列表逐次变长——正是注册进行中的快照。双重检查锁修掉，并写了一个**能真正复现该竞态**的测试
（把 bug 放回去验证测试确实会挂）。

> 并行还有个副作用：跑得快，你会更愿意跑全量，从而更早发现问题。串行 25 分钟的基线，
> 7 并发压到 4 分钟。

### 17. 上下文缓存命中率可以做到 90%，但要为它设计

每个 agent 的 system prompt + 工具 schema 是固定前缀，对话逐轮追加——天然适合前缀缓存。
实测命中率 **90.2%**（386 万输入 token 里 360 万命中）。

> 要点：**工具顺序必须确定**（`resolve()` 保持声明顺序）、system prompt 拼装无随机成分。
> 命中率低于 30% 说明有东西在打散前缀，值得查。

### 18. 真花钱的东西要两把独立开关

```yaml
live_tools_enabled: false      # 总闸
statuses: { sms.send: live }   # 单个工具
```

**两个都开才会真发。** 只标 live 而总闸关着，照样走模拟器。为这条写专门的测试——防的是手滑
或 agent 越权导致真扣钱。

### 19. 工具白名单是控制 prompt 长度的杠杆

每个 agent 只看得见白名单里的工具。工具少了，prompt 就不用解释无关流程。这是**保持每个 agent
prompt 短**的主要手段，比精简措辞有效得多。

### 20. 提防 prompt 膨胀

intake 从 2000 字符长到 18000。每一次增补都有正当理由（doctor 修 bug 加的、新需求加的），
**但总和是个问题**。定期检查，超预算就考虑再拆一个 agent。

## 六、需求沟通

### 21. 不要替客户过度建模人的环节

我照着原始文档做了四段式师傅回传（到达时间/检查结果/现场报价/完工时间）。客户看了说：

> "师傅上门后，师傅自己回复做完了，或者回复客户不愿意做，然后 AI 就发一个感谢短信就结束了。
> 不要那么多步骤。"

**一个工具、两种结果就够了。** 师傅在现场当场跟客户谈完，不需要 AI 在中间来回传话。

> 一般规律：**凡是"人和人当面就能解决"的环节，AI 不要插进去**。它只负责把人凑到一起，
> 和事后记录结果。

### 22. 客户会读到的业务文案，要按"能直接念出来"来写，并且放配置里

拒单理由、安全提示、收费说明——这些 agent 会原样转述给客户。写在配置里，写成完整的句子：

```yaml
reason: >-
  Our liability insurance does not cover work inside residential apartment and
  condo units, so we are not able to take on repairs there.
decline_guidance: >-
  说不能做和为什么，简短、不含糊。不要提出可以破例，不要暗示改个说法就行，
  不要让客户觉得找经理能翻案。
```

第二段（怎么说）和第一段（说什么）一样重要。

### 23. 需求会一直变，把改动批量化

这个项目做的过程中需求改了十几次（公司换了、语言换了、城市换了、收费顺序反了、保修加了人工
审核、资料收集从上传链接改成邮件……）。

> **对策**：每次改动落到"配置 + prompt + 状态机 + 场景 + 测试"五处，**一次改完再跑验收**。
> 边跑边改会让验收结果没有意义。

## 七、一个新 business 从零到可用的顺序

1. **先写业务规则表**（`business_rules.yaml`）——价格、工时、假期、拒接范围、升级规则。
   这是唯一事实来源，也是和客户对需求最快的方式：把表给他看，比问问题有效。
2. **画工单状态机**——一个 job 从进来到结束经历哪些状态，哪些迁移合法。
3. **列人必须做的决定**——哪些判断 agent 永远不能自己下（本项目里是：保修算不算数）。
   这些会变成"送去人工审核"的环节。
4. **切 agent**——按"客户视角的服务类型"切，不是按功能切。每个 agent 一个职责，共享规则抽片段。
5. **定工具白名单**——顺手就把 prompt 长度控制住了。
6. **写硬闸**——把第 3 步和禁止行为变成工具层的拒绝。
7. **写端到端场景**——从最上游入口进，覆盖每个硬闸所在的分支。
8. **跑自愈**——让 doctor 把 prompt 磨到全绿。
9. **最后才接真实服务**——两把开关，全绿之前不开。

前六步是设计，做扎实了后面很快。**第 7 步的场景质量决定第 8 步有没有用**——断言写松了，
doctor 会把 prompt 改成刚好糊弄过去的样子。
