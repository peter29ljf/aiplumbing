# 新 business 填空清单

按顺序填。**前六项是设计，填扎实了后面很快**；跳过任何一项，后面都会以"agent 行为古怪"
的形式回来找你。

把这份清单直接发给客户当需求提纲，比问开放式问题有效得多。

---

## 1. 公司事实 → `config/business_rules.yaml` 的 `company`

- [ ] 法定名称、对外电话、网站、服务区域
- [ ] 资质与保险（客户会问，agent 必须原样引用而不是自己编）
- [ ] 服务目录：每项服务的 id、名称、一句话说明
- [ ] 一单活是怎么走的（客户视角的三到五步）

> 这些通过 `rules.get_company_info` 提供给 agent。**不要写进 prompt**——公司信息会变，
> prompt 改了要重跑全部测试，配置改了不用。

## 2. 时间 → `schedule`

- [ ] 时区
- [ ] 工作日、营业时间起止
- [ ] "夜间"从几点算起（如果分时段计价）
- [ ] 周日/公众假期政策：完全不做？只接紧急？
- [ ] **本地法定假日清单**（不是通用的——BC 省没有 Boxing Day，安省有）

## 3. 钱 → `pricing`

每一项都要回答"多少、什么时候收、抵不抵、退不退"：

- [ ] 上门/到店基础费用
- [ ] 是否分时段计价，每档多少、什么条件
- [ ] 是否收订金：金额、可退否、抵扣什么
- [ ] 抵扣规则：接受报价怎么算、拒绝报价怎么算
- [ ] **退款的分界线是什么事件**（见 PLAYBOOK 第 5 条：选客户可感知的事件，不要选内部状态位）

## 4. 不接什么 → `service_policy`

这一项最容易漏，也最贵：

- [ ] 哪些物业类型/客户类型/工作类型不接
- [ ] 每一条的**理由，写成能直接念给客户听的整句**
- [ ] 有没有例外（本例：公寓小活不接，但公寓大工程接）
- [ ] 怎么拒：`decline_guidance` 要写清楚不许含糊、不许暗示破例

## 5. 人必须做的决定

**列出 agent 永远不能自己下的判断。** 这些会变成"送人工审核"的环节：

- [ ] 哪些判断必须由人做？（本例：保修算不算数——由当初做那单的师傅判）
- [ ] 送给谁？（原经手人 / 当班的人 / 主管）
- [ ] 找不到指定的人怎么办？（本例：转当班的，不是升级主管）
- [ ] 多久回复？agent 期间对客户说什么？

## 6. 工单状态机 → `config/ticket_states.yaml`

- [ ] 一单活从进来到结束经历哪些状态
- [ ] 每个状态能迁移到哪些状态
- [ ] 哪些是终态
- [ ] 哪些状态任何时候都能进（通常是"已升级"和"已关闭"）

> **画完对着每个 agent 的流程走一遍**，确认没有断头路。
> 这一步省下来，会在端到端测试时以"非法状态迁移"的形式加倍还回来。

## 7. 切 agent → `config/agents.yaml`

- [ ] 按**客户视角的服务类型**切，不是按功能切
- [ ] 每个 agent 一句话职责
- [ ] 谁能交接给谁
- [ ] 共享 prompt 片段有哪些（通用规则、工具纪律、交接、人员交接后的等待）
- [ ] **每个 agent 的工具白名单**——这是控制 prompt 长度的主要手段

## 8. 硬闸 → 工具层

把第 4、5 项和所有"绝对不能"变成工具的拒绝。每条硬闸要有：

- [ ] 触发条件
- [ ] 返回给 agent 的错误文案（**要写明该怎么做，它会照着自我纠正**）
- [ ] violation 类型名（断言层据此判失败）

## 9. 现场人员 → `config/world_seed.yaml`

- [ ] 名单、联系方式、技能、服务区域或所属门店
- [ ] 最大同时接单量
- [ ] 排班（谁在班上）

## 10. 种子数据

测试需要的客户档案：

- [ ] 新客户（查不到）
- [ ] 老客户（有历史工单）
- [ ] 触发每个特殊分支的客户（本例：保修有效的、保修排除的、保修过期的、同一次上门做了两种活的）
- [ ] 历史对话记录（客户会说"你们的人上次说过……"）

## 11. 端到端场景 → `scenarios/`

**从最上游入口进**，每条覆盖一个真实客户旅程。必须覆盖：

- [ ] 每个 agent 的主路径各一条
- [ ] **每个硬闸所在的分支各一条**
- [ ] 拒接的情况
- [ ] 客户中途反悔、取消、不肯决定
- [ ] 人工审核批准 / 不批准
- [ ] 外部依赖失败（支付失败、对方不回复、找不到人）

每条场景要写：

- [ ] 客户性格卡 + 事实卡 + 行为规则 + 结束条件
- [ ] 世界设定（时间、人员策略、支付结果、人工审核结论）
- [ ] 断言：工单终态、必须调用/禁止调用的工具、短信用途、以及 **judge 的语义评判问题**

> **断言写松了，自愈循环会把 prompt 改成刚好糊弄过去的样子。** 这一步的质量决定后面有没有用。

## 12. judge 的评判项

通用四条已经内置（语言一致、不编价格、不泄露内部信息、**不编造行为**）。加上本行业的：

- [ ] 这个行业里"说错话"的典型样子是什么？
- [ ] 有没有法规/资质要求 agent 必须说或必须不说的话？

## 完成后的验收顺序

```bash
python3 -m pytest -q                      # 工具层与管线，秒级
python3 scripts/check_llm.py              # 模型连通、tool calling、缓存
PYTHONPATH=src python3 -m <pkg>.testkit.runner scenarios/<suite>/01_*.yaml -v   # 单条端到端
PYTHONPATH=src python3 -m <pkg>.testkit.loop --suite <suite> --baseline-only    # 全量基线
PYTHONPATH=src python3 -m <pkg>.testkit.loop --suite <suite>                    # 自愈到全绿
```

**最后才接真实服务**：`config/tool_catalog.yaml` 里两把开关都打开，逐个工具切。
