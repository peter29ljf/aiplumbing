# 三层边界：哪些共用，哪些是套件，哪些每次重写

做第二个 business 时，**能原样用的比想象中多**——前提是知道界在哪。

这份文档描述的是 `flow/` 重写之后的架构。上一版写的是 5 个 agent + 编排器 + handoff 那套，
那套已经被换掉了：现在是**一条对话走一张节点图**，每个节点只带自己的指令和自己的工具。

## 分层

```
┌─ 第 1 层：引擎 `bat/runtime/` ──────── 共用，一行都不用改 ──┐
│  project.py     一个项目就是一个目录，路径全从这里解析      │
│  graph.py       读 flow.yaml，一次报出全部问题             │
│  engine.py      一轮对话：装配 prompt、发、收工具调用、推进  │
│  assemble.py    节点 prompt = always + goal + rules + 记忆  │
│  memory.py      跨节点存活的东西（tickets.tags 上的视图）    │
│  registry.py    @tool 注册、schema 生成、dispatch           │
│  world.py       两个后端共用的词汇表                        │
│  sim.py         模拟后端（内存，不出进程）                   │
│  llm.py         按角色调模型、重试、用量与缓存统计           │
│  harness.py     并行跑场景，收集全部失败                     │
│  diagnose.py    故障按来源分类 + 节点耗时表                  │
│  smells.py      慢轮次、重复调用、重复提问                   │
│  followup.py    24 小时回访循环，不放弃                      │
└─────────────────────────────────────────────────────────────┘

┌─ 第 2 层：套件 `bat/presets/` ──── 改词不改结构 ────────────┐
│  tools/service.py   16 个服务派单工具                       │
│    · crm 客户档案 / 历史                    ← 服务业通用     │
│    · calendar 日历与时段                    ← 预约类通用     │
│    · ticket 工单与 tags                     ← 任何行业都要   │
│    · sms / email / technician 通知          ← 任何行业都要   │
│    · escalate 转人 + schedule 回访          ← 任何行业都要   │
│    · rules 读 business_rules.yaml           ← 任何行业都要   │
│  rules/*.md         5 个成型写法，每个对应一次真实失败       │
│  always.md          每个节点都带的前言                       │
│  harness.yaml       测试参数和达标判定                       │
└─────────────────────────────────────────────────────────────┘

┌─ 第 3 层：行业 `bat/projects/<name>/` ── 每次重写 ──────────┐
│  flow.yaml            节点图：切几步、每步干什么、怎么分叉   │
│  rules/*.md           每个节点的指令，散文                   │
│  always.md            只在这门生意需要额外交代时才写         │
│  business_rules.yaml  价格、工时、拒接范围、升级规则         │
│  tools/*.py           这门生意自己要的工具                   │
│  scenarios/*.yaml     端到端场景 + 节点级场景                │
└─────────────────────────────────────────────────────────────┘
```

## 引擎有多干净

**一个项目就是一个目录。** 引擎里没有一处知道任何一门生意的事——这不是运气，是通用化时
专门去掉的：原来只靠三行 import 和三个路径常量就绑死在一家水管公司上。

证据是那 45 条引擎测试**原样搬过来还能过**。它们测的是节点边界、什么能跨步骤存活、分支枚举、
收尾闸——和哪门生意无关，而**它们不需要改写这件事本身就是论据**。

新项目里要继续守住的约束：

> **代码里不写 `if 紧急:`。** 分流由节点调 `step.finished` 说出口子名字决定，引擎只负责按图
> 推进。而口子名字是**按节点生成的枚举**，所以说出一个不存在的分支是不可能的，不是被劝阻的。

## 「上门」和「到店」的差别在第 2 层

两种履约形态共用客户档案、工单、通知、回访，差别集中在这几处：

| | 上门（somebody goes out） | 到店（the customer comes in） |
|---|---|---|
| 地点 | 客户地址，要算服务区、路程 | 我们的场地，要算场地产能 |
| 人员 | 有服务区、有技能、会在路上 | 绑定场地、有专长、不移动 |
| 时段 | 一个人的日历空档 | **场地 × 人 × 椅位/诊室** 的空档 |
| 紧急 | 派单、找人、定金、退款窗口 | 一般是加急/插队，或者当天加号 |
| 提醒 | 出发通知、ETA | 到店提醒、迟到/爽约处理 |

生成器**自己会认出来**这件事。牙医那个项目第一轮就说：预设工具是上门那一套
（"addresses, one technician, travelling diary"），到店需要自己的日历和通知工具——
这条从没进过它的提示词，它是读了 `presets/tools/service.py` 看出来的。

配置里加：

```yaml
service_delivery: in_store        # on_site | in_store | both
locations:
  - { id: "main", name: "...", address: "...", chairs: 2 }
```

到店的项目自己写 `tools/<name>.py`，把 `calendar.find_slots` 换成认识椅位的那个版本。
**不要改预设工具**——那 16 个的措辞是被二十三条场景验证过的，改了等于把证据作废。

## 迁移时最容易漏的四件事

1. **工单状态是行业的，不是通用的。** 别复用上一个行业的状态表，重画。牙医那张里没有
   "Technician Dispatched"，因为没人出门。
2. **`must_not_say` 禁的是那句会后悔的话，不是那个词。** 每一种说法都能出现在拒绝里：
   禁 `"refund"` 会让「我不能承诺退款」失败，禁 `"scrub"` 会让「别搓它」失败——而后者
   正是业主给的安全提示原话。
3. **一句话从哪个节点说出来，性质不同。** "you're all set" 从报时间的节点说是撒谎，
   从下单的节点说是实话。用 `must_not_say_in` 指定节点。
4. **节点只读工单，从不读对话记录。** 所以任何一步学到而没写下来的东西就是没有了。这条
   是节点级测试成立的前提，也是生成的 flow 最常见的失败方式。
