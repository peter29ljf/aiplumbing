# 开发方法与成本

PLAYBOOK 讲**会踩到什么坑**，这份讲**按什么顺序做、每一步值不值得**。

先读这份。它能省掉的时间比后面几份加起来都多——不是因为讲得更深，而是因为它讲的是**顺序**，
而顺序错了，后面所有经验都得再踩一遍才学得会。

---

## 一、最贵的一条：先验证仪器，再验证产品

做水管那个项目的第一天，八小时里**约四个半小时花在"让测试台可信"上**，中间整份失败清单作废重来。

根因不复杂：客户模拟器偶尔吐坏 JSON，而那看起来跟"客户不耐烦挂断"一模一样。于是测试台的抖动
伪装成了业务结论，自愈循环照着假结论去改一个本来没错的 prompt。等发现的时候，前面几小时得出的
每一条"真失败"都不能信了。

**本来可以花 20 分钟避免**：

> 写完第一个场景，**先把同一个场景连跑 10 次**，看通过率是不是 10/10。
> 不是 10/10 就先修测试台，一个 agent 都别碰。

这个动作成本几乎为零。它回答的是一个比"agent 对不对"更靠前的问题：**这台秤准不准。**

推广开就是一句话：**任何用 LLM 判分的系统，第一件事是量化判分器自己的方差。** 你的测试台里有
几个 LLM（被测 agent、模拟人、裁判），就有几个噪音源，而它们的失败长得都像业务失败。

配套的两条：

- **测试台自己的故障必须显式上报**，不能静默地表现成"这个场景没过"（见 PLAYBOOK 10）
- **一次运行不算证据**，判定要建立在多轮之上（见 PLAYBOOK 10b）

## 二、四种检查手段，成本差两个数量级

这是这类项目里最容易搞错的取舍。同一个 bug，用哪种手段发现，成本可以差 100 倍。

| 手段 | 单次成本 | 能抓什么 | 抓不到什么 |
|---|---|---|---|
| **静态一致性检查** | 几秒，几乎免费 | prompt 之间互相矛盾、prompt 和配置对不上、写死的数字、非法状态转移 | 任何需要执行才暴露的问题 |
| **工具层单测** | 秒级，免费 | 硬闸有没有漏、状态机合不合法 | agent 会不会正确使用它们 |
| **单 agent + stub 下游** | 中，约端到端的 1/5 | 单条链路的逻辑、工具用法、措辞 | 交接断链 |
| **端到端** | 高 | 交接断链、跨 agent 的状态传递 | —— |

**关键在于：越靠上的手段越便宜，而且能抓到的东西是靠下的手段抓不到的**，不是"低配版"。

### 静态一致性检查——最大的效率洼地

水管项目做到第八小时，我在**读** prompt 的时候发现一个 bug：

- `_shared/core_rules.md` 说"师傅出发后不退款"
- `agents/emergency.md` 说"确认短信发出后不退款"
- `config/business_rules.yaml`（唯一真相源）说以短信为准

**三处不一致，其中一处是早就被业主改掉的旧规则。** 这会直接导致赔钱，而且很可能是那条链路
一直抖动的来源之一——同一件事 prompt 里有两个说法，模型每次挑哪个看运气。

它是**读出来的，不是跑出来的**。而这种检查完全可以自动化：让一个 LLM 读全部 prompt +
业务规则配置 + 状态机，只回答"哪里互相矛盾"，不改任何东西。**几秒钟，零测试运行。**

值得做成固定动作的静态检查：

1. **矛盾扫描**——所有 prompt 之间、prompt 与配置之间
2. **硬编码数字扫描**——prompt 里出现的每个价格/时长/期限，是不是都该从工具读
3. **状态转移扫描**——prompt 里提到的每个状态跳转，在状态机里合不合法
4. **旧词扫描**——换了公司名、地区、价格之后，有没有哪份文件漏改

第 4 条是水管项目真踩过的：公司改名后 `core_rules.md` 漏了一处，**agent 对着客户说了旧公司名**。

### 端到端要留给验收，不要用来迭代

分段测试全绿、合起来断链，是这类项目的典型失败模式，所以端到端**不能省**（见 PLAYBOOK 11）。

但它太贵，不适合用来迭代。水管项目一天跑了 **~156 次端到端运行**（每次是一整段多轮对话加裁判，
粗估 20-40 次 LLM 调用），**换来 3 个 agent bug**。其中大部分运行是在重复验证已经好了的链路。

正确的分工：

- **迭代期**：单 agent + stub 下游。快、便宜、定位准
- **验收期**：端到端。慢、贵，但抓断链

### 录制-回放：把回归和探索分开

活的 LLM 模拟人有两个用途，被混在一起了：

- **探索**——每次措辞不同，能发现没想到的问题。要高温度
- **回归**——确认改动没弄坏别的。要**可复现**

高温度的模拟器做回归是矛盾的：结果本身就不稳定，你分不清是改坏了还是运气差。

**把跑通的对话存成固定脚本，回归时直接回放，不启动模拟器。** 没有模拟器就没有模拟器噪音，
结果 100% 可复现，成本降一个数量级，可以每次改动都跑。代价是不适应 agent 的新行为——agent
换了问法脚本就对不上，需要重录。

**回放做回归，活模拟器做探索。** 水管项目全程用活模拟器，两个用途混在一起，这是它跑得慢的
第二个原因。

## 三、能进工具层的规则，就别进 prompt

水管项目跑到最后有个数字很说明问题：

> **所有硬闸，一次都没有被绕过。prompt 里的规则，时灵时不灵。**

每一条能在工具层强制的规则，就是一条**不用写进 prompt、不用花 LLM 调用去测、也不会被模型
忘记**的规则。这是一份三重收益：

1. **可靠性**——代码不会偶尔忘记
2. **prompt 长度**——见下
3. **测试量**——不需要为它设计场景反复跑

举个真实的例子。"公寓里的小活不做（保险不覆盖）"这条规则，水管项目在 intake、small_job、
emergency 三份 prompt 里各写了一遍，**共 59 行**。如果改成：预约工具在
`property_type=apartment` 且 `category=small` 时直接拒绝，那 prompt 里**一句话就够**，
而且保证不会漏。

### 顺带说 prompt 长度：你看到的不是 agent 收到的

水管项目的 prompt 文件加起来 820 行。但因为公共片段会拼进每个 agent，**五个 agent 累计
吃进 1577 行**。

```
agent 实收 = 自己的 prompt + 它 include 的所有公共片段
```

**公共片段每加 1 行，实际成本是 4-5 行。** 所以：

- 公共片段要比专属 prompt 更严格地控制长度
- 自愈循环改公共片段时要特别留意——doctor 为了修一个场景往公共片段加 20 行，五个 agent 同时
  变长
- 定期扫重复。水管项目扫出**约 20% 的内容是跨文件重复**，其中两处是一字不差的复制

重复不能简单删掉——同一条规则在多个 agent 里写，往往是**故意的二道防线**。正确做法是抽成
共享片段多处 include：保护还在，但改一处改全部。

## 四、推荐顺序

| | 做什么 | 为什么在这个位置 |
|---|---|---|
| 1 | **量化测试台方差**：一个场景连跑 10 次 | 20 分钟，省掉几小时和一次结论作废 |
| 2 | **工具层 + 硬闸 + 单测** | 最可靠的一层，且能减少后面所有环节的工作量 |
| 3 | **静态一致性检查** | 几秒抓一类 bug，零运行成本 |
| 4 | **单 agent + stub 迭代** | 便宜、定位准 |
| 5 | **录制-回放做回归** | 可复现，能高频跑 |
| 6 | **端到端只做验收** | 贵，但抓断链，不可省 |
| 7 | **自愈循环** | 前面都稳了才有意义 |

水管项目实际走的是 **2 → 6 → 7 → 1（被迫）→ 4/5（一直没做）**。

**把最便宜的第 1、3 步跳过了，用最贵的第 6 步去发现它们本该发现的问题。** 这是那一天里
效率损失的全部来源。

## 五、这套方法在业界的位置

避免误会：**这套方法整体是主流的**，不是自创的。

| | 主流程度 |
|---|---|
| eval 套件驱动开发 | 完全主流。LangSmith / Braintrust / Langfuse / W&B Weave 都做这个 |
| LLM 扮演用户做多轮压测 | 主流且有公开标杆。τ-bench 就是这个范式：模拟用户 + 工具调用 + 政策遵守，域是零售/航空客服 |
| LLM-as-judge | 主流。它的噪音问题也是公认的 |
| 工具全模拟 + 沙箱 | 主流 |
| 多 agent handoff | 主流。OpenAI Agents SDK、LangGraph、CrewAI 都是这个结构 |
| 危险动作在工具层设闸 | 主流建议，但**真正做到的团队少** |

真正加出来的只有三样，都在测试台一侧：

1. **自愈的防作弊哈希护栏**——让 LLM 改 prompt 不新鲜，但"跑前对配置/代码/场景/测试做 SHA256，
   跑完比对，动了就整次作废"这层少见。而它是必需的：模型修 bug 的第一反应就是改测试或改规则
2. **失败按来源分类**（测试台故障 / 框架拦截 / agent 犯错）——大多数团队只有"过/不过"。
   这条决定了什么该自动修、什么该报给人
3. **多轮判定 + 自适应确认**——大多数团队跑一次就下结论

## 六、不推荐的做法

**prompt 自动优化框架**（DSPy / TextGrad / OPRO 这一类）：把 prompt 当参数、对着指标优化。

对窄任务（分类、抽取、推理）效果好。**对这类项目不推荐**：

- 业务 prompt 是**政策文档**，200 行讲的是"什么情况下该怎么办"，不是一个可优化的模板
- 优化出来的 prompt 往往人读不懂，而这类 prompt **需要人能读、能审、能对着业务规则核对**
- 业务规则会一直变，每次变都要重新优化

**更合适的是"强模型读完整对话记录后自由改 markdown"**。水管项目里 doctor 两次给出的诊断都
比人读 prompt 猜的准——它看见的是**工具返回值被误读**，人看见的只是措辞歧义（见 PLAYBOOK 14）。

## 七、省钱的几个具体开关

1. **模拟人用便宜模型。** 客户/师傅/主管模拟器的任务是"按人设说人话、别越界"，扮演质量对
   结论的影响远小于被测 agent 本身。
2. **裁判抽样跑，别每次都跑。** LLM 裁判是最贵也最吵的一环。水管项目里 **3 个 bug 全部是
   硬断言抓到的，没有一个是裁判发现的**。裁判该跑在硬断言全过的运行上，或者抽样。
3. **为上下文缓存设计。** 公共片段放最前、每次都一样，命中率能到 90%（见 PLAYBOOK 17）。
4. **验证一个机制不要跑全量套件。** 挑最相关的几个场景（见 PLAYBOOK 10c）。
5. **真花钱的外部服务用两把独立开关**，全绿之前不开（见 PLAYBOOK 18）。
