# 开发方法与成本

PLAYBOOK 讲**会踩到什么坑**，这份讲**按什么顺序做、每一步值不值得**。

先读这份。它能省掉的时间比后面几份加起来都多——不是因为讲得更深，而是因为它讲的是**顺序**，
而顺序错了，后面所有经验都得再踩一遍才学得会。

---

## 一、最贵的一条：先验证仪器，再验证产品

做水管那个项目的第一天，八小时里**约四个半小时花在"让测试台可信"上**，中间整份失败清单作废重来。

根因不复杂：客户模拟器偶尔吐坏 JSON，而那看起来跟"客户不耐烦挂断"一模一样。于是测试台的抖动
伪装成了业务结论，自愈循环照着假结论去改一个本来没错的规则文件。等发现的时候，前面几小时得出的
每一条"真失败"都不能信了。

**本来可以花 20 分钟避免**：

> 写完第一个场景，**先把同一个场景连跑 10 次**，看通过率是不是 10/10。
> 不是 10/10 就先修测试台，一个节点都别碰。

这个动作成本几乎为零。它回答的是一个比"agent 对不对"更靠前的问题：**这台秤准不准。**

推广开就是一句话：**任何用 LLM 判分的系统，第一件事是量化判分器自己的方差。** 你的测试台里有
几个 LLM（被测 agent、模拟人、裁判），就有几个噪音源，而它们的失败长得都像业务失败。

### 后来又踩了三次，全是同一类

重写那一天，三条"最难缠的失败"最后都是**测试写错了**：

- 场景禁了 `"refund"` 这个词，于是「我不能承诺退款」——正确答案——判失败
- 换成禁 `"full refund"`，于是「您要求全额退款这件事已经记下了」判失败
- 生成器造牙医诊所时，禁了 `"scrub"`，于是「别搓它」判失败——那是业主给的安全提示原话

**`must_not_say` 禁的是那句会后悔的话，不是那个词。** 每一种说法都能出现在拒绝里。

还有一次更隐蔽：`"you're all set"` 从报时间的节点说出来是撒谎，从下单的节点说出来是实话。
断言查的是整段对话，于是后一个节点说的真话，判了前一个节点的失败。**用 `must_not_say_in`
指定节点。**

配套的三条：

- **测试台自己的故障必须显式上报**，不能静默地表现成"这个场景没过"
- **一次运行不算证据**，判定要建立在 `--repeat 4` 之上
- **失败要按来源分类**，见第三节

## 二、四种检查手段，成本差两个数量级

同一个 bug，用哪种手段发现，成本可以差 100 倍。

| 手段 | 单次成本 | 能抓什么 | 抓不到什么 |
|---|---|---|---|
| **图的静态校验** | 毫秒，免费 | 分支指向不存在的节点、规则文件缺失、工具不存在、节点不可达 | 任何需要执行才暴露的问题 |
| **引擎单测** | 秒级，免费 | 节点边界、什么能跨步骤存活、收尾闸 | agent 会不会正确使用它们 |
| **节点级场景** | 约 15 秒 | 一个节点的判断和措辞 | 交接断链、状态没写下来 |
| **端到端** | 约 40 秒一条 | 断链、跨节点的状态传递 | —— |

**越靠上的手段越便宜，而且能抓到的东西是靠下的手段抓不到的**，不是"低配版"。

### 图的静态校验——最大的效率洼地

`graph.load()` 一次报出全部问题。生成器写完 `flow.yaml` 就跑它，报错原样喂回去。牙医那个
项目第一次构建被打断，重跑时它一次收到 11 条缺失，一轮补齐。

**不用另写校验，也不用花一次模型调用去发现一个拼错的节点名。**

### 节点级场景——重写那天最划算的一个改动

场景可以从图中间起步，工单预置好该有的状态：

```yaml
start:
  node: warranty_check
  known: { phone: "604-555-0913", known_customer: "yes", issue: "..." }
```

测一个节点从 **20 次模型调用降到 2 次，一轮 510 秒降到 66 秒**。

它成立的前提是：**节点只读工单，从不读对话记录**。哪天这条不成立了，这些测试就失效——
而那本身值得知道。

它还有一个意外用处：**同一个节点，单独测 4/4、整链路 2/4，那道鸿沟本身就是诊断。** 差别在
它拿到的工单状态，也就是前一个节点该写而没写的东西。重写那天最大的一次跃升（12/22 → 26/28）
就是这么找到的——`greeting` 从来没把客户来干什么写到工单上。

### 端到端要留给验收，不要用来迭代

分段测试全绿、合起来断链，是这类项目的典型失败模式，所以端到端**不能省**。

但它太贵，不适合用来迭代。**迭代用节点级，验收用端到端。**

## 三、失败按来源分类，这条决定什么该自动修

harness 把每一条失败分三类，它们的答案完全不同：

| | 意思 | 怎么办 |
|---|---|---|
| **config** | 它根本没被给到手段——工具缺失，或规则文件和工具清单互相矛盾 | **这是自己的 bug，必须修** |
| **model** | 工具和指令都在眼前，它做了别的 | 把规则写利，或者接受这是模型的天花板 |
| **harness** | 场景或运行器写错了，不是 agent | 改场景。**不要动 agent** |

**配置类故障必须归零，这条不可放宽。** 真实例子：`no_number` 节点的规则让它报上门费，
`always.md` 禁止说任何没查过的数字，而这个节点没有任何查询工具。夹在中间它干脆什么都不答，
还花了 19 秒编那句拒绝。给它 `rules.get_service_options` 之后，均值 21.9 秒降到 5.3 秒。

**模型类故障才是换模型的依据**，而且是唯一的依据。

**harness 类故障意味着测试错了。** 忍住不要为了让一个坏测试通过去改 agent。

## 四、能进工具层的规则，就别进规则文件

水管项目跑到最后有个数字很说明问题：

> **所有硬闸，一次都没有被绕过。规则文件里的规则，时灵时不灵。**

每一条能在工具层强制的规则，就是一条**不用写进提示词、不用花模型调用去测、也不会被忘记**的
规则。三重收益：可靠性、提示词长度、测试量。

重写之后又多了两个机制，都是"把事情从模型手里拿走"：

**`remembers`** —— 工具声明哪些字段该留在工单上，引擎自己抄过去。原来靠模型记得写，
结果是客户给了电话号码，查询用了它，步骤结束，号码跟着消息一起没了，下一步又问一遍。

**收尾闸 `_undone`** —— 终端节点必须调完它手上所有的活才允许说结束语。`booking` 曾经
在没建单、没发短信、没通知师傅的情况下说了「您都安排好了」，而那就是对话的结尾。

**推动 `_still_here`** —— 一个节点回复两次还没结束，引擎就问它在等什么。`warranty_check`
查完老工单就该交棒，却跟一个要退款的客户吵了四轮。

## 五、推荐顺序

| | 做什么 | 为什么在这个位置 |
|---|---|---|
| 1 | **量化测试台方差**：一个场景连跑 10 次 | 20 分钟，省掉几小时和一次结论作废 |
| 2 | **画图，让 `graph.load()` 过** | 毫秒级，抓掉一整类 bug |
| 3 | **工具层 + `remembers` + 硬闸 + 单测** | 最可靠的一层，且减少后面所有环节的工作量 |
| 4 | **节点级场景迭代** | 便宜、定位准，15 秒一轮 |
| 5 | **端到端只做验收** | 贵，但抓断链，不可省 |
| 6 | **自愈循环** | 前面都稳了才有意义 |

水管项目实际走的是 **3 → 5 → 6 → 1（被迫）→ 4（第二天才做）**。

**把最便宜的第 1、2、4 步跳过了，用最贵的第 5 步去发现它们本该发现的问题。** 这是那一天里
效率损失的全部来源。

## 六、什么时候停

自愈循环要有停止条件，否则它会在噪音上跑一整夜。

```yaml
usable:
  every_scenario_clean: true
  min_pass_rate: 0.95
  config_faults: 0
  stop_after_flat_rounds: 2
```

**「进步」是跟最好成绩比，不是跟上一轮比。** 86% → 84% → 85% 是**两轮**白跑，不管第三个数
看起来比第二个好。跟上一轮比的话，中间那个凹陷会把计数清零，循环就永远停不下来。

这条是实测出来的：分数在 84–86% 之间跳了三轮，而**真正的信号是失败从哪个节点移到了哪个节点**，
不是总分。生成器造牙医诊所时也复现了同一形状：63% → 65% → 65%，然后按这条规则停了。
停下来是对的——它让我去找"修复者拿不到什么"，答案是那五份成型写法当时还没写。

## 七、省钱的几个具体开关

1. **在便宜的端点上开发，定论才换。** 同一个模型家族，Bailian 对 DeepSeek 官网是 82% 对
   84–90%，缓存命中 60% 对 84%。**这个差距正是要在便宜端点上开发的理由**——在它上面暴露的
   失败几乎全是自己的规则文件或场景写错了，而那正是值得找的那一类。
2. **为上下文缓存设计。** 每个节点的提示词每次都一样，命中率能到 84%。命中率掉了，说明有东西
   在稳定部分前面塞了新文本——那是唯一能让小提示词重新变贵的方式。
3. **模拟人用便宜模型。**
4. **验证一个机制不要跑全量套件。** 挑最相关的几条，或者用节点级场景。
5. **两个计费表分开算。** 建 agent 花的钱（Anthropic）和跑 agent 花的钱（模型 provider）
   加在一起，就看不出该攻哪边了。

## 八、这套方法在业界的位置

避免误会：**这套方法整体是主流的**，不是自创的。eval 套件驱动开发、LLM 扮演用户做多轮压测
（τ-bench 就是这个范式）、LLM-as-judge、工具全模拟、危险动作在工具层设闸——都是主流。

真正加出来的只有三样，都在测试台一侧：

1. **失败按来源分类**（配置 / 模型 / 测试台）——大多数团队只有"过/不过"。这条决定了什么该
   自动修、什么该报给人，也是唯一能回答"该不该换模型"的东西
2. **节点级场景**——从图中间起步，把一个节点的测试从 20 次调用降到 2 次
3. **多轮判定 + 跟最好成绩比的停止条件**——大多数团队跑一次就下结论

---

## 九、不推荐的做法

**prompt 自动优化框架**（DSPy / TextGrad / OPRO 这一类）：把提示词当参数、对着指标优化。

对窄任务效果好。**对这类项目不推荐**：业务规则文件是**政策文档**，讲的是"什么情况下该怎么办"，
不是一个可优化的模板；优化出来的东西人读不懂，而这类文件**需要人能读、能审、能对着业务规则核对**。

**更合适的是"强模型读完整对话记录和故障分类后自由改 markdown"**——这正是这套生成器的
iterate 阶段在做的事。
